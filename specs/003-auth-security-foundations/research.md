# Research: Auth & Security Foundations

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-10-14

Each entry records the decision, why it was chosen, and what else was considered. Numbers chosen
here (limits, lifetimes) are the defaults the implementation and tests use; all are configurable in
`appsettings.json` under `Security:` and `Limits:`.

---

## R1. Who does authentication: Supabase Auth or the ASP.NET backend?

- **Decision**: Use Supabase **only as a managed PostgreSQL database**. Authentication, sessions and
  authorization are done in the existing ASP.NET Core backend with **ASP.NET Core Identity**
  (`AddIdentityCore`, user-only EF Core store) over Npgsql. Supabase Auth (GoTrue), the Data API
  (PostgREST) and the Supabase client libraries are not used.
- **Rationale**:
  - The spec asks for a username sign-in. Supabase Auth signs people in by email or phone. A
    username would have to be faked as an email (`alice@users.invalid`), which is fragile.
  - Supabase Auth gives the browser a JWT access token plus a refresh token, normally kept in
    `localStorage`. The constitution (VII) requires session tokens that page scripts cannot read
    (`HttpOnly` cookies). Meeting that with Supabase Auth would still need a backend-for-frontend
    to hold the tokens, so the backend is involved anyway.
  - A JWT stays valid until it expires (default 1 hour). SC-005 needs revocation within 1 minute
    and FR-011 needs sign-out to take effect immediately. Server-side sessions that are checked on
    every request meet both without extra work.
  - Supabase's breached-password check is only on paid plans. We need it on every plan (FR-005).
  - Identity is a vetted framework library (no hand-rolled crypto, VII). It gives password
    hashing, per-account lockout, an authenticator (TOTP) token provider and a security stamp.
    It also supports a username-only user.
  - Supabase still covers what the owner asked for: a cloud-hosted database that the owner manages
    directly, including adding users ([R6](#r6-provisioning-invite-only-accounts-in-the-database)).
- **Alternatives considered**:
  - *Supabase Auth with synthetic emails and admin-only user creation* ("Disable signups"). This
    was rejected for the token-storage, revocation and username reasons above. It would also put
    the security logic in a second system that tests cannot run locally without Docker.
  - *A hand-written user store over plain Npgsql (no EF Core)*. This means fewer packages, but we
    would have to re-implement and maintain the parts of Identity we rely on (store contracts,
    lockout, security stamp). That costs more than the extra packages do.

## R2. Password storage and policy (FR-005, FR-007)

- **Decision**:
  - Use Identity's `PasswordHasher` (PBKDF2-HMAC-SHA512, per-user salt), with the iteration count
    raised to **210,000** (the OWASP Password Storage Cheat Sheet value for PBKDF2-SHA512).
  - The policy follows NIST SP 800-63B: **12–128 characters**, no composition rules, and the
    password must not contain the username. Unicode is allowed and normalized to NFKC before
    hashing.
  - Every new password is checked against **Have I Been Pwned Pwned Passwords**. This uses the
    k-anonymity range API (`GET https://api.pwnedpasswords.com/range/{first 5 hex of SHA-1}` with
    `Add-Padding: true`).
  - The check **fails closed**. If HIBP cannot be reached, the user sees "We couldn't check this
    password right now, please try again in a minute", and the event is audited.
- **Rationale**: PBKDF2 at the OWASP iteration count meets the constitution's "strong password
  hash" requirement without a third-party hashing package (Principle V). The k-anonymity API sends
  only 5 hex characters of a hash and never the password or the username, so nothing personal
  leaves the server (Tech Constraints: Privacy). Failing closed is the only reading of "MUST reject
  breached passwords" that holds even when HIBP is down. HIBP outages are rare and only affect the
  one-time setup step.
- **Alternatives considered**:
  - *Argon2id via a NuGet package* (Konscious, Isopoh). This adds a dependency, and Argon2id's
    memory hardness would cost a lot of RAM on a small host for little gain at this scale.
  - *A bundled list of common passwords*. It only covers the top N passwords, while the HIBP check
    covers the full breach corpus.
  - *Failing open if HIBP is down*. This would break the MUST in FR-005.

## R3. Second verification step (FR-001, FR-004)

- **Decision**:
  - Use **TOTP (RFC 6238; 6 digits, 30-second step, SHA-1)** through Identity's
    `AuthenticatorTokenProvider`. This works with any authenticator app.
  - The 160-bit secret is generated by Identity. It is stored **encrypted at rest** with ASP.NET
    Data Protection (purpose `MacroCounter.Totp.v1`) by overriding the store's authenticator-key
    methods.
  - **Replay is blocked**: the last accepted code and the time it was accepted are stored, and the
    same code is refused for 5 minutes. TOTP attempts count toward the same lockout as passwords
    ([R7](#r7-brute-force-and-enumeration-protection-fr-006-fr-020-sc-006)). Enrolment
    confirmation allows 5 wrong codes per setup session, after which the setup session is revoked.
  - During setup the user sees a **QR code** (for desktop users who scan with their phone), the
    **setup key** as text, and an `otpauth://` **link** (for people setting up on the phone that
    also runs the authenticator).
- **Rationale**: The constitution allows "strong password hash … plus TOTP". The spec's
  Assumptions choose TOTP and leave passkeys for later. Identity's provider accepts codes up to
  ±2 time steps, which tolerates clock drift. Replay blocking is added because ASVS requires
  one-time use of codes and Identity does not track it.
- **Alternatives considered**:
  - *Passkeys/WebAuthn*: out of scope per the spec.
  - *Otp.NET*: it reports the matched time step, which gives cleaner replay protection, but it is
    one more dependency. Rejecting a code that was just accepted gives the same protection.
  - *Email or SMS codes*: the spec does not collect email or phone numbers.

## R4. Sign-in flow shape and first-time setup (US1, FR-004, FR-006)

> **Superseded by [004 research R1](../004-security-qol/research.md#r1-two-step-sign-in-replaces-the-single-request-fr-001--fr-010-supersedes-003-r4)
> (two-step sign-in).** The setup steps below still apply.

- **Decision**:
  - The sign-in form has **one request** with `username`, `password` and an optional `code`.
  - **Normal sign-in**: the password and the TOTP code are checked together. Any failure, or a
    missing code, returns the same `401 sign_in_failed`. The response never shows whether the
    password alone was right.
  - **First sign-in**: the person puts their **temporary code** in the password field and leaves
    the code field blank. A valid temporary code returns `setup` and starts a short-lived *setup
    session*. Setup has three steps, in order: (1) set a password, (2) enrol TOTP, (3) read and
    acknowledge "What is sent to Claude". Only after step 3 is the setup session swapped for a
    **new** full session, with a new ID to prevent session fixation.
  - If someone sets a password and then abandons setup, signing in again with that password
    resumes setup. This is only allowed before the account's **setup deadline** (72 hours after it
    was invited or reset).
- **Rationale**: Checking all factors in one request avoids a "password was correct" signal,
  which a two-step password-then-code flow would give (FR-006). The notice step meets the
  constitution's Accountability rule: friends must be told what is sent to Claude before they
  first use AI lookup.
- **Alternatives considered**: *Separate password and code screens*. This is a common pattern, but
  it reveals whether the password was correct and needs a second pending state.

## R5. Sessions: storage, lifetime, revocation (FR-009 – FR-012, SC-005)

- **Decision**:
  - Use ASP.NET Core **cookie authentication** with a server-side `ITicketStore`
    (`PostgresTicketStore`).
  - The cookie is `__Host-mc_session` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, no
    `Domain`). It holds only a 256-bit random session key, protected by Data Protection.
  - The database stores the **SHA-256 of that key**, the user ID, the kind (`setup` | `full`),
    created/last-seen times, an absolute expiry, and the serialized ticket.
  - **Every** authenticated request loads the session joined to the user and refuses it if the
    session is missing, past its idle or absolute limit, from a different security stamp, or the
    user is disabled.
  - `last_seen_at` is written at most once per minute.
  - **Lifetimes**: full session idle **24 hours**, absolute **7 days**; setup session idle and
    absolute **15 minutes**.
  - **Sign-out** deletes the session row. **Sign out everywhere**, a password reset or a disable
    deletes all of the user's rows and rotates the security stamp.
- **Rationale**:
  - Checking the database on every request makes revocation **immediate**, which is stricter than
    SC-005's 1 minute. That covers sign-out, a disable by the owner, and a reset.
  - The cost is one indexed primary-key lookup per API call. That is negligible for fewer than 20
    users when the host and Supabase are in the same region.
  - Hashing the key means a leaked sessions table cannot be replayed.
  - `__Host-` stops subdomains from setting the cookie, and `SameSite=Strict` blocks cross-site
    sends.
  - The lifetimes come from the documented risk analysis that ASVS 5.0 V7.3 asks for:
    - The server holds no health data, only AI quota.
    - Every sign-in needs a second factor.
    - Logging must stay quick on a phone (Principle IV).
    - Local logging works without a server session (see R9), so a 24-hour idle limit mostly
      affects AI lookup.
- **Alternatives considered**:
  - *Stateless encrypted cookies with `SecurityStampValidator` at a 1-minute interval*. These meet
    SC-005 but cannot revoke a single signed-out cookie.
  - *JWT bearer tokens*: readable by scripts, and not revocable.
  - *ASVS 4 L2 lifetimes (12 h absolute / 30 min idle)*: rejected for usability. Re-entering a
    TOTP code several times a day would stop people logging food.

## R6. Provisioning invite-only accounts "in the database" (FR-002, FR-003, FR-008, SC-011)

- **Decision**:
  - The owner manages accounts by running **SQL functions in a private `macro_admin` schema**,
    from the Supabase SQL editor (as `postgres`). The functions are `invite_user`, `reset_user`,
    `disable_user`, `enable_user`, `unlock_user`, `revoke_sessions`, plus read-only views. See
    [contracts/owner-procedures.md](./contracts/owner-procedures.md).
  - `invite_user` and `reset_user` generate a **temporary code** with `pgcrypto.gen_random_bytes`:
    20 characters from a 32-character unambiguous alphabet (100 bits), shown as
    `XXXX-XXXX-XXXX-XXXX-XXXX`. They store only its SHA-256 hash, set a 72-hour setup deadline,
    and return the code **once**. The owner passes the code to the friend in person or over a
    trusted channel.
  - The code is single-use: it is cleared when the password is set.
  - The application's database role (`macro_app`) has **no `INSERT` on `users`**. It also has no
    `UPDATE` on `username`, `role` or `disabled_at`, and no access to `macro_admin`.
- **Rationale**: This matches the spec literally: there is no account-creation endpoint, and new
  users are added through the database. It also enforces the rule at the database level, so even
  a fully compromised app process cannot create or re-enable accounts. The temporary code is a
  high-entropy random secret, so a fast hash (SHA-256) is appropriate, as for reset tokens in
  OWASP guidance. The PBKDF2 hash is kept for user-chosen passwords. Each procedure is one line of
  SQL, which keeps SC-011 (under 5 minutes) easy to meet.
- **Alternatives considered**:
  - *Owner hand-writes `INSERT` statements*: error-prone, and the owner cannot compute
    Identity-format hashes in SQL.
  - *A `dotnet run -- users add` CLI*: this still needs the owner's database credentials, adds code,
    and goes against "via the database".
  - *An admin web screen*: excluded by the spec.

## R7. Brute-force and enumeration protection (FR-006, FR-020, SC-006)

- **Decision**: Three layers. **All of them return the identical response**:
  `429 rate_limited` with `Retry-After` and the message "Too many attempts. Try again later."
  1. **Per source IP**: ASP.NET Core `RateLimiter` fixed window, **20 sign-in attempts per 15
     minutes**, also applied to setup endpoints.
  2. **Per normalized username, whether or not the account exists**: an in-memory sliding window
     of **10 failures per 15 minutes**, then refuse for 15 minutes. Unknown usernames hit the
     limit exactly like real ones, so a lockout reveals nothing (FR-006).
  3. **Per account, persisted**: Identity lockout, **10 consecutive failures → 15-minute lockout**.
     It survives restarts. The owner can clear it with `macro_admin.unlock_user`.

  Timing is evened out: for unknown usernames and for temporary-code checks, a dummy PBKDF2
  verification runs, so every path does one hash. Usernames are trimmed and compared
  case-insensitively, and the canonical stored form is lowercase `^[a-z0-9._-]{3,32}$`.
- **Rationale**: This meets SC-006 even when the correct password is entered after 10 failures.
  The in-memory layers reset on restart, but an attacker cannot trigger restarts, and layer 3 is
  persisted. Someone could deliberately lock an account by failing on purpose. That risk is
  accepted at this scale, and the owner can unlock it.
- **Alternatives considered**:
  - *A database-backed attempts table for every attempt*: write amplification and more code. The
    persisted Identity counter already covers restarts.
  - *CAPTCHA*: a third-party dependency, and it would send data to an outside service.

## R8. AI cost protection (FR-021, FR-022, SC-008, Principle VI)

- **Decision**: AI estimate endpoints run these checks in order: authenticated session → per-user
  burst limit (in-memory token bucket, **6 per minute**) → **database quota reservation in one
  transaction**.

  The quota reservation:
  - adds 1 to `ai_usage_daily(user_id, utc_day)` only if the count is below **30 per user per
    day**;
  - adds 1 to `ai_usage_global_daily(utc_day)` only if the count is below **200 per day**;
  - checks that the sum of the global rows for the current UTC month is below **3,000 per month**.
    The global day row is row-locked, so concurrent requests are serialized.

  Any failure rolls back and returns `429 quota_exceeded` with `scope` (`user_daily`,
  `global_daily`, `global_monthly`) and `resetAt` (UTC; the UI shows local time). A request is
  counted **before** Claude is called and is not refunded, because a failed call may still have
  been billed. Ceiling hits are audited (US5.3).
- **Worst-case spend (what the count ceiling means in dollars)**: The ceiling counts requests,
  not dollars. This is the worst case per request with the current configuration, at Claude
  Opus 5.5's list price of $4 per million input tokens and $20 per million output tokens
  (checked 2026-10-14):

  | Part of the request | Worst case | Cost |
  |---|---|---|
  | Output, including thinking | `MaxTokens = 16000` in `Ai/ClaudeEstimator.cs` | 16,000 × $20/M = $0.320 |
  | Input: photo | At most 1568 px on the long edge, about (w × h) / 750 ≈ 2,500 tokens | |
  | Input: prompt, schema, note | Under 3,500 tokens together | 6,000 × $4/M ≈ $0.024 |
  | **Per request** | | **≈ $0.35** (configured as `Limits:Ai:WorstCaseCostPerRequestUsd`) |

  With the default limits, the worst case is **$70 per day** (200 × $0.35) and **$1,050 per
  month** (3,000 × $0.35). Typical requests use far fewer output tokens, so real spend should be
  a small fraction of this, but the cap is the guarantee. The app logs both figures at startup
  (tasks T096 and T101).

  This assumes a failed attempt is not billed. The SDK retries 429, 5xx and connection errors up
  to 2 times. If a timed-out generation were billed and then retried, one lookup could cost up to
  3 × $0.35. To tighten the cap, the owner can lower `GlobalMonthly` or `MaxTokens`. Re-check
  these figures whenever the model, `MaxTokens` or the photo size limit changes.
- **Rationale**: Reserving first means total usage can never go over the limits, even under
  concurrency (SC-008). Counting requests keeps the module simple and testable. The table above
  turns the count limits into a known worst-case bill that the owner can tune. All limits are
  configurable. Manual entry is client-side and never calls these endpoints (FR-022).
- **Alternatives considered**:
  - *Token-based spend accounting from Claude's `usage` field*: more exact, but it is only known
    after the call, so a ceiling could be overshot. It can be added later if needed.
  - *In-memory quotas*: lost on restart, which would let usage go over the daily cap.

## R9. Per-account local data on a shared browser (FR-016 – FR-018, SC-007)

- **Decision**:
  - Each account gets **its own IndexedDB database**, `macro-counter.u.<userId>`, using the same
    schema and migrations as today. The user ID is a server UUID, never the username.
  - A small device database, `macro-counter-device`, stores the **active account** (`userId`,
    `username`, `role`) and a `legacyAdopted` flag. It is accessed only through a new
    `DeviceRepository` (Principle III).
  - **At launch**:
    - Online with a valid session: open that user's database.
    - Online without a session: show the sign-in screen, and no local data is opened.
    - **Offline, or the server/database unreachable**: open the last active account's database so
      logging and history keep working. Server features then show "Sign in or reconnect to use AI
      lookup".
  - **Sign-out** clears the active-account marker, keeps the user's database, and reloads the page
    so no in-memory state survives.
  - **Legacy adoption**: on the first full sign-in on a browser that has the pre-feature
    `macro-counter` database and `legacyAdopted` unset, the data is copied into that user's
    database **only if the user's role is `owner`**. The copy runs in one transaction per store,
    and record counts are checked before the legacy database is deleted and the flag is set.
- **Rationale**: Separate databases make it impossible for a query bug to leak across accounts,
  which a key prefix could allow. Reusing the existing migrations means no schema change for food
  data.

  Owner-only adoption resolves a conflict in the spec. FR-018 says "the first account that signs
  in", while US4 scenario 3 says the data is adopted by the owner and no other account can adopt
  it. Before this feature the app was single-user, so the legacy data must belong to the owner. If
  a friend happened to sign in first on the owner's browser, the friend would get the owner's
  health data. The plan follows US4.3, and FR-018 was reworded to match on 2026-10-14 (owner
  decision).

  The offline grace period meets the spec's offline edge case and Principle III.
- **Residual risk**: separation is logical, not cryptographic. A person with developer-tools
  access to the same browser profile could read another account's IndexedDB. Encrypting at rest
  with a key derived from the password is out of scope, and this risk is documented in the threat
  model.
- **Alternatives considered**:
  - *A key prefix inside one database*: one forgotten filter leaks data.
  - *Deleting local data on sign-out*: forbidden by FR-017.

## R10. CSRF, origin checks and CORS (FR-010, FR-029)

- **Decision**:
  - **CSRF**: use ASP.NET Core antiforgery, with an `HttpOnly` cookie `__Host-mc_af` and the
    request token returned in the JSON of `GET /api/auth/session` and of each sign-in or setup
    response. The SPA keeps the token in memory and sends it as `X-CSRF-Token` on every unsafe
    request. An endpoint filter validates it on **all** non-GET `/api` endpoints, including
    sign-in, to stop login CSRF.
  - **Origin check**: middleware refuses unsafe `/api` requests whose `Origin` is not in
    `Security:AllowedOrigins`. If `Origin` is absent and `Sec-Fetch-Site` is present and not
    `same-origin`, the request is refused too.
  - **CORS**: the CORS middleware is **not registered**. The only allowed origin is the app's own,
    and same-origin requests need no CORS headers. Cross-origin reads are therefore always blocked
    by the browser, which is the strictest form of an explicit allowlist (never `*`).
- **Rationale**: This is defense in depth on top of `SameSite=Strict`. Returning the token in the
  response body avoids a script-readable cookie.
- **Alternatives considered**: *A double-submit `XSRF-TOKEN` cookie readable by scripts*. It works,
  but it exposes a token to page scripts with no benefit.

## R11. Browser hardening headers and HTTPS (FR-027, FR-028, US7)

- **Decision**: One middleware adds these headers to **every** response in all environments
  except where noted:

  - `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self';
    img-src 'self' data: blob:; connect-src 'self'; worker-src 'self'; manifest-src 'self';
    font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self';
    frame-ancestors 'none'; upgrade-insecure-requests`. In Development,
    `upgrade-insecure-requests` is omitted and the Vite dev server's websocket origin is allowed
    in `connect-src`.
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: no-referrer`
  - `X-Frame-Options: DENY` (for older browsers)
  - `Cross-Origin-Opener-Policy: same-origin`
  - `Cross-Origin-Resource-Policy: same-origin`
  - `Permissions-Policy: camera=(self), microphone=(), geolocation=(), payment=()`. Feature 002's
    in-app camera uses `getUserMedia` on the app's own origin, so the camera is allowed for `self`
    only; no other origin or embedded frame may use it. (Updated 2026-10-14 when 002 was merged.)
  - `/api/*` responses get `Cache-Control: no-store`.
  - `index.html` gets `Cache-Control: no-store`, so the back/forward cache cannot show a
    signed-in screen after sign-out (US1.3). A `pageshow` handler also re-checks the session
    when a page is restored from that cache.

  In production, `UseHsts` sends `max-age=31536000; includeSubDomains` and `UseHttpsRedirection`
  redirects HTTP to HTTPS. The host's "HTTPS only" setting is also turned on.
  `appsettings.Production.json` sets `AllowedHosts` to the real host name, so it is never `*`.
  `ForwardedHeaders` is enabled with `ForwardLimit = 1` so the client IP and the original scheme
  come from the host's TLS proxy.
- **Rationale**: The Vite production build emits only external scripts and styles, and
  vite-plugin-pwa's `injectRegister: 'auto'` uses an external `registerSW.js`. That means a strict
  CSP with no `'unsafe-inline'` works. React sets styles through the CSSOM, which CSP does not
  block. The QR code is inline SVG markup (R13), so it needs no `img-src` exception. Zod 4 would probe for `new Function` to compile schemas, which a CSP without `'unsafe-eval'` reports as a violation; `z.config({ jitless: true })` is set at startup (`src/zodConfig.ts`), found by the end-to-end CSP test.
- **Alternatives considered**: *NWebsec or a similar header package*: one more dependency for
  about 30 lines of code.

## R12. Server-side store layout, least privilege and Supabase hardening (FR-019, FR-026, FR-030)

- **Decision**:
  - All tables live in a private schema, `macro`, that is **not** exposed by Supabase's Data API.
    The Data API is turned off in the project settings, because nothing uses it. As a second
    layer, RLS is enabled on every table, and everything is revoked from `anon`,
    `authenticated` and `public`.
  - **RLS policies for the app role**: RLS blocks every role that has no matching policy, and
    `macro_app` does not own the tables, so it needs explicit policies to read its own data.
    `macro_admin.grant_app_role(role)` creates them:
    - one `for all … using (true) with check (true)` policy per table, **scoped to that role
      only**;
    - on `audit_events`, only a `for insert … with check (true)` policy, matching its
      insert-only grant.

    Every other role (`anon`, `authenticated`, any new role) still sees nothing. Grants remain
    the real limit on what the app can do; the policies only let it through RLS. `BYPASSRLS` is
    not used: Supabase's `postgres` role is not a superuser and cannot grant it, and a policy
    keeps the exception visible in the schema.
  - `pgcrypto` lives in the `extensions` schema on Supabase, but usually in `public` on a plain
    local install. Every `macro_admin` function therefore sets
    `search_path = macro, extensions, public, pg_temp`.
  - The app connects as a dedicated `macro_app` login role with least-privilege grants (see
    [data-model.md](./data-model.md#database-roles-and-grants)). It uses **Supavisor session
    mode** over IPv4 with `SSL Mode=VerifyFull` and Supabase's root CA, which is public and
    committed under `backend/MacroCounter.Api/certs/`.
  - Supabase **Network Restrictions** limit database access to the host's outbound IPs and the
    owner's IP.
  - Schema changes are **EF Core migrations**. The owner applies them as an idempotent SQL script
    (`dotnet ef migrations script --idempotent`) through `psql` or the SQL editor. The app never
    migrates at startup, and `macro_app` has no DDL rights.
  - The migrations create the owner procedures and the grants with raw SQL. Supabase-only
    statements (the roles `anon`/`authenticated`, and the `pg_cron` schedule for
    `macro_admin.purge_expired()`) are guarded so the same scripts also run on plain local
    PostgreSQL.
  - Audit entries are kept for **180 days**. `macro_app` can only `INSERT` audit rows. Only the
    owner can read or delete them, through the purge job.
- **Rationale**: Each layer limits the damage if another fails. The application cannot read back
  or change audit history, and cannot create users. Committing a public CA certificate is not a
  secret leak.
- **Alternatives considered**:
  - *Tables in `public` with RLS*: one mistaken policy would expose them through PostgREST.
  - *Connecting as `postgres` or with the service-role key*: far too much privilege.
  - *DbUp or plain SQL files*: EF Core is already needed for the Identity and Data Protection
    stores.

## R13. New dependencies (Principle V)

| Package | Replaces / why needed |
|---|---|
| `Npgsql.EntityFrameworkCore.PostgreSQL` 10.x | PostgreSQL provider for EF Core. Required by Supabase. |
| `Microsoft.AspNetCore.Identity.EntityFrameworkCore` 10.0.x | Vetted user store for Identity (password hashing, lockout, TOTP, security stamp). Avoids hand-rolled auth. |
| `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` 10.0.x | Keeps the Data Protection key ring in the database, so cookies, antiforgery tokens and TOTP secrets survive restarts and redeploys. |
| `Microsoft.EntityFrameworkCore.Design` 10.0.x (build-time only, `PrivateAssets=all`) | `dotnet ef` migrations tooling. |
| `Microsoft.Extensions.TimeProvider.Testing` (test only) | `FakeTimeProvider` for session expiry, lockout windows and quota day boundaries. |
| `uqr` 0.1.x (frontend) | Renders the TOTP enrolment QR code as SVG with no dependencies. Without it, desktop users would have to type a 32-character key, which works against SC-002. |

Data Protection keys are encrypted at rest with an X.509 certificate supplied as a secret
(`DataProtection:CertificatePfxBase64` and its password) in production. In Development and Testing
they are stored unencrypted.

**Supply chain**: NuGet lock files are turned on (`RestorePackagesWithLockFile`, and restore uses
`--locked-mode` in the check script). `dotnet list package --vulnerable --include-transitive` and
`npm audit --audit-level=high` are added to `scripts/check.ps1`. A high or critical finding fails
the gate (SC-010, VII).

**CI**: A GitHub Actions workflow (`.github/workflows/ci.yml`) runs the same `scripts/check.ps1`
on every pull request to `master` and every push to `master`.
- It runs on `ubuntu-latest` with a `postgres:17` service container, so Docker is needed only on
  GitHub's runner, never locally.
- It uses no repository secrets, because no test contacts Claude, HIBP or Supabase.
- Actions are pinned to commit SHAs, and the workflow token is read-only.
- Branch protection on `master`, which makes the check required before merging, is a repository
  setting the owner turns on.

## R14. Test database without Docker (FR-032, Spec: Environment)

- **Decision**: Backend integration and endpoint tests run against a **local PostgreSQL 17**
  (`winget install PostgreSQL.PostgreSQL.17`). A test fixture reads an admin connection string
  from `MACROCOUNTER_TEST_PG` (default `Host=localhost;Username=postgres`). It creates a
  throwaway database `macro_test_<guid>`, applies the migrations, creates the `macro_app` role
  for that database, runs the tests **as `macro_app`** (so the grants are tested as well), and
  drops the database afterwards. The Playwright end-to-end tests use a `macro_e2e` database
  that `scripts/e2e-db.ps1` resets and seeds. The live Supabase project, the live HIBP API and
  the live Claude API are never contacted from tests.
- **Rationale**: Docker is not installed on the development machine, which rules out
  Testcontainers and the Supabase CLI local stack. Plain PostgreSQL runs the same SQL as Supabase
  apart from the guarded Supabase-only statements (R12). Running as `macro_app` proves the
  least-privilege design (no `INSERT` on users, insert-only audit).
- **Alternatives considered**:
  - *Testcontainers*: needs Docker.
  - *SQLite or EF InMemory*: different SQL dialect; would not run the owner procedures, grants or
    locking.
  - *A second Supabase "test" project*: network-dependent and slow, and it would put test data in
    the cloud.

## R15. Hosting (Spec: Environment, FR-027)

- **Decision**: The reference deployment is **Azure App Service (Linux, B1, one instance)** in the
  same region as the Supabase project.
  - It is deployed with `dotnet publish` plus zip deploy, which needs no Docker.
  - It provides managed TLS on `*.azurewebsites.net` (or a custom domain) and "HTTPS Only".
  - Secrets go in App Settings, ideally as Key Vault references.
  - The code is host-agnostic: the only host assumption is the forwarded-headers configuration.
- **Rationale**:
  - The existing stack is .NET on Windows, and there is no Docker locally.
  - Using **one instance** keeps the in-memory rate limiters correct; the database quotas are
    correct with any number of instances.
  - The B1 tier keeps the app warm ("Always On"), so sign-in latency meets SC-001.
- **Alternatives considered**:
  - *Fly.io or Render containers*: cheaper, but they need a Dockerfile and remote builds.
  - *Self-hosting on the home PC with a tunnel*: ties availability to the PC and widens the
    attack surface.

## R16. Public status vs. configuration leakage (FR-013)

- **Decision**: Add a public `GET /api/health` that returns `{"status":"ok"}` and nothing else.
  The existing `GET /api/status` (`aiAvailable`) becomes **authenticated**, because it reveals
  whether an API key is configured, which is configuration.
- **Rationale**: FR-013 limits public endpoints to sign-in and "a minimal availability check that
  reveals nothing about users or configuration".
